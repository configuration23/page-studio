# Справка портала: как устроена

Статус: **сделано**. Общая справка — `/admin/help`, в инспекторе — короткий итог и
ссылка на раздел.

## Решение

Справка живёт **одним документом**, а не размазана по элементам:

- `/admin/help` — страница с разделами: как всё устроено, авторизация, адреса,
  события и цели, частые ошибки, затем по разделу на каждый вид элемента;
- у каждого раздела свой якорь: `#kind-edit`, `#kind-button`, `#auth`, `#api` — ссылку
  можно дать человеку или открыть из инспектора;
- в инспекторе у элемента — **две строки итога** (что это) и ссылка
  **«Справка по элементу →»** на раздел вида, в новой вкладке. Редактор при этом не
  теряет несохранённое состояние;
- ссылка ведёт на **вид**, а не на конкретный элемент: разделы общие для всех страниц,
  и ссылка не ломается при переименовании элемента.

## Один источник

`src/help.ts`:

- `HELP` — запись на каждый вид (`Record<Kind, Entry>`): название, описание, свойства,
  частые ошибки;
- `guidePage()` — собирает страницу: общие разделы (маркдаун) + разделы по видам;
- `helpSummaries()` — короткие итоги, которые встраиваются в страницу админки для
  инспектора.

Методы, вызовы и примеры **генерируются** из модели (`VALUE_KINDS`, `EVENTS_OF`), поэтому
справка не расходится с кодом. В примерах — шаблон: `<портал>`, `<страница>`, `<id>`,
`<sid>`, `<PORTAL_TOKEN>`.

## Правило для новых элементов и методов

Новый вид или метод — изменение контракта. В том же коммите:

1. запись в `HELP` (`src/help.ts`) — иначе TypeScript не соберётся: `Record<Kind, Entry>`
   требует запись на каждый вид;
2. методы и примеры появятся на странице справки автоматически;
3. `docs/BACKEND.md` — если появился новый вызов со стороны бэкенда;
4. `CHANGELOG.md` — строка об изменении;
5. `pnpm test` — зелёные.
